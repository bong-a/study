01

같은 조회 횟수인데, 왜 값이 달라질까요?

“이 사람이 이 상품을 몇 번 보았나요?”라는 질문은 단순해 보입니다. 그런데 계산하는 사람마다 답이 달라질 수 있습니다. 오늘 하루를 셀지, 지금부터 다섯 시간 전까지 셀지, 같은 상품만 셀지부터 정하지 않았기 때문입니다.

모델은 이렇게 계산한 숫자를 단서로 삼습니다. 이 숫자를 피처라고 부릅니다. 좋은 피처를 만들려면 숫자 하나뿐 아니라 누구의 기록인지, 무엇을 세는지, 언제까지의 기록인지를 함께 정해야 합니다.

키 · Key
기록의 주인을 구별하는 표식입니다. 사용자 ID 하나일 수도, 사용자와 상품 ID의 조합일 수도 있습니다.
집계 · Aggregation
여러 기록을 합계·평균·횟수 같은 값으로 줄이는 계산입니다.
시간 창 · Window
집계에 넣을 시간 범위입니다. ‘최근 5시간’처럼 시작과 끝이 있습니다.
백필 · Backfill
이미 보관한 기록으로 과거 시점의 피처를 나중에 다시 계산하는 작업입니다.
읽는 방법
원문의 핵심은 짧게 짚고, 아래에서 새로 만든 숫자와 표로 작동 원리를 따라갑니다. 예시의 사용자·상품·금액은 실제 Airbnb 데이터가 아닙니다.
02

Chronon이 대신 맡으려는 일

2023년 글은 피처 관리 때문에 모델 개발이 늦어지는 문제에서 출발합니다. 피처를 직접 기록하면 데이터가 쌓이기를 기다려야 하고, 별도로 재계산하면 학습과 서비스가 달라질 수 있습니다. Chronon은 계산 정의를 공유합니다.

원문 예시는 사용자가 항목을 최근 5시간 동안 본 횟수입니다. 이후 설명은 시간 정확도, 입력 데이터의 종류, 온라인·오프라인 환경, 세 가지 계산 도구, 집계 확장 기능 순서로 이어집니다. Snapshot은 일별 갱신, Temporal은 시점별 계산·재현 기준입니다.

입력은 이벤트, 엔티티 상태, 과거 버전을 보존하는 누적 이벤트로 설명합니다. 계산 도구는 GroupBy·Join·StagingQuery이며, 집계에는 시간 창·분류별 집계·배열 펼치기·시간순 선택이 있습니다. 결론은 공통 정의에서 학습과 서비스용 피처 생성을 연결한다는 것입니다.

누적 이벤트는 이전 버전이 남아 있어 최신 파티션으로도 과거를 재구성할 수 있다는 점이 일반 상태 스냅샷과 다릅니다.

‘선언형’이라는 말은 조리법에 가깝습니다

도시락을 주문한다고 생각해 봅시다. “누구의 주문을 모으고, 어떤 재료를 쓰고, 몇 인분을 만들 것인가”를 정하는 일과, 냉장고·가스레인지·배달 순서를 운영하는 일은 다릅니다. 여기서 선언은 원하는 계산의 조건을 적는 쪽입니다. 이 비유에서 계산 규칙이 조리법이고, 실행 기반이 주방입니다.

따라서 사용자가 먼저 분명히 해야 할 것은 “이 피처는 무엇을 뜻하는가”입니다. 잘못된 조리법을 적어 두면 자동화된 주방도 다른 음식을 만듭니다. 플랫폼을 도입해도 피처의 의미와 기준 시각을 정하는 책임까지 사라지지는 않습니다.

03

최근 5시간의 조회 수를 직접 세어 봅시다

설명용 가상 데이터

6월 10일 오후 2시에 사용자 민수가 상품 A를 볼 가능성을 예측한다고 가정합니다. 이 연습에서는 오전 9시 이상, 오후 2시 미만을 최근 5시간으로 정합니다. 모든 기록은 발생 직후 사용 가능했다고 가정합니다.

정답은 2회입니다.
시간·사용자·상품 조건을 모두 만족한 기록만 셉니다.

이제 오후 3시의 같은 질문을 생각해 보세요. 시간 범위는 오전 10시부터 오후 3시 직전으로 이동합니다. 09:20 기록은 빠지고 14:10 기록이 들어갑니다. 횟수는 다시 2회지만, 계산에 사용한 기록은 달라졌습니다. 숫자만 비교해서 같은 계산이라고 판단하면 안 되는 이유입니다.

스스로 확인하기 · 상품 구분을 빼면 몇 회인가요?

오후 2시 기준 민수의 모든 상품 조회를 세면 09:20의 A, 11:10의 B, 13:30의 A로 3회입니다. 상품별 관심과 사용자 전체 활동량은 서로 다른 피처입니다.

이 표는 시간 창을 배우기 위한 직접 계산 예시입니다. 특정 Chronon 설정의 실제 실행 결과를 재현한 표는 아닙니다.

04

시간을 얼마나 촘촘하게 맞출 것인가

공식 GroupBy 문서에서 Snapshot은 자정 기준의 일별 값, Temporal은 서비스의 실시간 갱신과 과거 시점에 맞춘 재계산을 연결하는 설정입니다. 이는 모델의 정답률을 뜻하지 않습니다. GroupBy 문서 ↗

새로 만든 가격 예시

같은 상품의 가격도 시간에 따라 달라집니다

00:0010,000원

하루 시작 가격을 저장합니다.

12:0012,000원

판매자가 가격을 바꿉니다.

14:00예측 시점

어느 가격을 모델에 줄까요?

일별 값으로 서비스한다면

오후 2시에도 저장된 10,000원을 모델이 받는다고 가정합니다. 과거 학습을 재현할 때도 10,000원이 실제 조건에 맞습니다. 더 최신인 12,000원으로 바꾸면 학습 환경이 달라집니다.

변경 직후 갱신한다면

정오의 변경이 서비스에 반영됐다면 오후 2시에는 12,000원이 맞습니다. 이 경우 오래된 10,000원을 붙이는 것이 당시 입력과의 차이가 됩니다.

따라서 질문은 “어느 숫자가 더 최신인가?”에서 끝나지 않습니다. 그 순간 예측 모델이 실제로 받도록 설계된 값이 무엇인가?까지 물어야 합니다. 갱신 주기는 서비스 운영 방식과 함께 해석해야 합니다.

오래됨과 누출을 구분하세요.
오래된 피처는 최근 변화를 놓칠 수 있습니다. 미래에야 알게 된 피처는 예측 당시의 조건을 어깁니다. 둘은 원인도, 해결 방법도 다릅니다.

‘일별 파티션’이라는 이름만 보고 판단하지 마세요

날짜별 폴더는 정리 방식입니다. 폴더 안에 시각이 있는 모든 조회 기록이 들어 있을 수도 있고, 하루 끝 상태 한 장만 들어 있을 수도 있습니다. 전자는 시간 조건으로 골라낼 여지가 있지만, 후자는 중간 상태를 모릅니다. 파티션 날짜와 데이터가 표현하는 시간을 따로 확인해야 합니다.

모으고, 붙이고, 미리 다듬기

GroupBy는 피처를 정의하는 주요 도구입니다. 조건에 따라 집계 없이 필드를 그대로 피처로 사용하거나, 여러 계산을 연결할 수도 있습니다. GroupBy ↗

Join의 왼쪽 입력은 과거 피처를 계산할 대상과 시각을 제공합니다. 오른쪽에는 결합할 피처 정의를 둡니다. 따라서 ID뿐 아니라 어느 시점의 단서를 붙일지를 정하는 역할도 합니다. Join ↗

StagingQuery는 복잡한 SQL 전처리를 표현할 때 쓰며 배치로 갱신됩니다. Join에 필요한 여러 키와 시각을 준비하는 것이 문서의 대표 용도입니다. StagingQuery ↗

Join이 모델을 학습시키는 것은 아닙니다.
이 단계의 결과물은 모델이 배울 수 있도록 정리한 입력 표입니다. 단서를 만드는 과정과 그 단서로 모델을 학습시키는 과정을 구분하면 전체 흐름이 쉬워집니다.

08

데이터에서 학습과 서비스까지

이 그림을 처음 볼 때 모든 영어 이름을 외울 필요는 없습니다. 왼쪽은 재료, 가운데는 계산 규칙, 오른쪽은 결과를 쓰는 곳이라는 순서부터 읽으면 됩니다.

그림 이해를 위한 가상 주문서

“민수의 최근 조회 수를 알려 주세요”

  1. 재료 선택: 민수의 조회 기록을 찾습니다. 상품 가격도 필요하면 상태 기록을 추가로 찾습니다.
  2. 조건 확인: 어느 사용자와 상품인가, 최근 몇 시간인가, 기준 시각은 언제인가를 확인합니다.
  3. 결과 전달: 지금 검색을 처리한다면 현재 서비스에 주고, 과거 검색을 연습한다면 학습용 행에 붙입니다.
  4. 점검: 값이 갑자기 비거나 달라졌다면 원시 기록과 계산 조건을 거슬러 올라갑니다.

온라인은 이용자의 요청에 응답하는 환경이고, 오프라인은 쌓인 기록을 한꺼번에 처리하는 환경입니다. 인터넷 연결 여부를 뜻하는 말로 읽으면 헷갈립니다. 같은 질문을 두 환경에서 일관되게 다루려는 구조라고 이해하면 됩니다.

09

시간 집계를 설계할 때 확인할 네 가지

가상 조회 사례에 적용하는 일반적인 설계 질문

앞의 예시에서 민수·상품 A의 오후 2시 조회 횟수와 오후 3시 조회 횟수는 모두 2회였습니다. 하지만 사용한 기록은 달랐습니다. 피처 이름과 숫자가 같다는 이유만으로 같은 계산이라고 판단하면 안 됩니다.

  1. 원시 시각 확인:날짜만 저장했는지, 각 조회가 발생한 시각도 보존했는지 살펴봅니다.
  2. 데이터의 뜻 확인:개별 이벤트 모음, 특정 순간의 상태, 이미 계산한 합계는 서로 다른 재료입니다.
  3. 갱신 조건 확인:하루 단위 값을 제공하는지, 새 이벤트를 반영하는지 학습과 실제 서비스의 조건을 맞춥니다.
  4. 제공 가능 시각 확인:이벤트가 예측 전에 발생했더라도 늦게 도착했다면 당시에는 사용할 수 없었을 수 있습니다.

기록 단위가 바뀌면 질문도 다시 확인합니다

가상으로 상품별 조회 기록을 고객별 전체 활동량으로 합치면, ‘상품 A에 관심이 있는가’와 ‘최근 많이 활동했는가’가 섞일 수 있습니다. 시간을 맞추는 일과 함께 사용자·상품 같은 집계 기준도 유지해야 합니다.

이 질문들은 특정 조직의 데이터 구조가 아니라, 앞서 만든 가상 표를 실제 시스템 설계에 연결해 보기 위한 일반적인 점검 항목입니다.

시간 기준을 올바르게 정의해도 피처의 예측력이 자동으로 보장되지는 않습니다. 정확히 무엇을 계산했는지 확인한 뒤, 그 값이 목적에 도움이 되는지 따로 평가해야 합니다.
10

세 질문에 답할 수 있으면 핵심을 잡았습니다

1. 날짜별 파일에 저장하면 하루 중간 값은 절대 만들 수 없나요?

아닙니다. 각 이벤트의 시각과 필요한 기록이 보존되어 있으면 시간 조건을 적용할 수 있습니다. 날짜별 파일이라는 보관 방식과, 하루 끝 상태만 남긴다는 정보 손실을 구분해야 합니다.

2. Temporal을 선택하면 예측 정확도가 자동으로 높아지나요?

그런 뜻이 아닙니다. 더 세밀한 시간 기준으로 계산하는 설정입니다. 예측 품질은 피처의 의미, 모델, 데이터 품질 등에도 달려 있습니다. 실제 서비스의 갱신 방식과 맞는지도 확인해야 합니다.

3. 이벤트 시각이 예측 이전이면 언제나 안전한가요?

발생은 이전이어도 늦게 수집되어 예측 당시에는 사용 불가능했을 수 있습니다. 이 점검은 시간 기준을 실제 운영에 적용할 때 필요한 추가 질문입니다. 이 설명만으로 Chronon이 모든 지연 도착과 장애 상황을 완벽히 복원한다고 단정하지 않습니다.

좋은 피처 정의는 숫자의 이름보다 구체적입니다.
누구의 무엇을, 어느 시간 범위에서, 어떤 갱신 조건으로 계산하는지까지 적습니다.

2023년 원문과 현재 공식 문서를 구분해 읽었습니다. 문서에 있는 세부 설정은 이후 바뀔 수 있으므로, 실제 구현에서는 사용 버전의 동작을 확인해야 합니다.

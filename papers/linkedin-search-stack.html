01 / QUERY UNDERSTANDING

사용자가 쓴 단어 뒤의 조건을 읽는다

검색창에 쓰는 말은 데이터베이스의 필드명과 다릅니다. “집에서 일하고 싶다”를 “원격근무”라는 조건으로 해석하면, 서로 다른 표현으로 적힌 공고도 찾을 수 있습니다.

검색어를 바꿔 보세요직접 만든 설명용 예시 · 모델 실행 아님

“집에서 일할 수 있는 데이터 분석 직무”

직무: 데이터 분석근무 방식: 원격
Data Analyst · Remote

공고에 “집에서”라는 표현이 없어도, 근무 형태와 직무가 맞으면 관련 후보가 될 수 있습니다.

핵심: 같은 단어가 있는지에 더해, 같은 뜻인지 살펴봅니다.

LinkedIn은 흩어진 개체명 추출 모델들을 통합하고, 질의와 프로필 문맥을 함께 해석하는 LLM을 사용합니다. 의도 분류, 조건 추출, 질의 재작성을 연결해 검색에 쓸 구조화된 신호를 만듭니다. [2]

정확한 이름·개체 검색에는 키워드 경로를, 모호한 질의에는 의미 해석 경로를 사용하는 라우팅도 유지합니다. [1]

02 / THE SEARCH PIPELINE

넓게 찾고, 자세히 읽고, 순서를 정한다

도서관에 비유하면 이해하기 쉽습니다. 먼저 서가에서 관련 책을 추리고, 그 책들의 내용을 자세히 비교해 읽을 순서를 정합니다.

Retrieval · 후보를 찾는 일

문서를 미리 숫자 벡터로 표현해 두면, 새 검색어의 벡터와 빠르게 비교할 수 있습니다.

“관련 있을 법한 책을 서가에서 가져오기”

Ranking · 순위를 매기는 일

추려진 문서와 검색어를 함께 읽어, 세부 조건까지 맞는지 더 비싼 계산으로 확인합니다.

“가져온 책을 펼쳐 보고 읽을 순서 정하기”

조금 더 깊게: 벡터 검색은 어떻게 학습할까?

Bi-encoder는 질의와 문서를 따로 인코딩합니다. LLM 판정으로 찾은 어려운 정답·오답을 대조학습과 마진 손실에 활용합니다. 운영에서는 GPU 기반 전수 벡터 검색을 수행합니다. [1]

예컨대 표현이 달라 놓친 정답은 더 가깝게, 단어만 비슷한 오답은 더 멀게 학습시키는 식입니다. 전수 벡터 비교와 모든 문서를 언어모델로 다시 읽는 것은 계산량이 다릅니다.

03 / QUALITY BEFORE MODELS

먼저 “좋은 검색 결과”의 기준을 맞춘다

모델을 바꾸기 전에 채점표가 필요합니다. 예를 들어 “원격근무”를 요청했는데 주 5일 출근 공고가 나왔다면, 직무가 정확하더라도 좋은 결과라고 볼 수 있을까요? 이런 판단을 일관되게 정의해야 합니다.

01 / 기준제품 정책

관련성 0–4점 정의

02 / 합의PM 기준 데이터

사람 간 κ ≥ 0.8

03 / 확장LLM 평가자

8B 모델로 증류

04 / 피드백지속 평가·학습

하루 수천만 쌍 채점

κ는 가중 Cohen’s kappa로, 사람들의 채점 일치도를 나타냅니다. 평가 결과는 검색 품질 측정과 학습 데이터 생성에 쓰입니다. [1]

온라인 모델로 지식 전달

랭커는 관련성뿐 아니라 클릭·지원 등도 학습합니다. 여러 교사 모델의 예측을 작은 0.6B SLM으로 증류합니다.

평가자와 실시간 랭커는 역할이 다릅니다.

평가자는 채점 기준을 대규모로 적용하는 역할, 랭커는 사용자의 요청에 빠르게 점수를 주는 역할입니다. 증류는 교사의 판단 패턴을 더 작은 학생에게 학습시키는 방법입니다.

채점이 잘 맞는다는 것과 사용자 만족은 같을까?

자동 평가 점수는 채점 기준을 얼마나 잘 따르는지 보여줍니다. 실제 만족도를 확인하려면 온라인 실험과 사용자 행동도 함께 봐야 합니다. 클릭률만 높아도, 관련성 점수만 높아도 충분하다고 단정할 수 없습니다.

이 문단은 결과를 읽기 위한 일반적인 해설입니다.

04 / LESS WORK AT REQUEST TIME

속도의 비밀은 “매번 읽는 양”을 줄이는 것

후보가 많으면 같은 공고를 여러 검색 요청에서 반복해서 읽게 됩니다. 공고가 바뀌기 전까지 재사용할 수 있는 표현을 만들어 두면, 요청 시점의 일이 줄어듭니다.

모델 자체를 줄이기

뉴런·어텐션 헤드·레이어를 구조적으로 제거하고 다시 학습합니다. GPU가 실제로 덜 계산하게 만드는 방식입니다.

입력을 짧게 만들기

별도 모델이 공고를 미리 요약합니다. 요약 길이와 랭킹 판단의 보존을 함께 고려합니다.

모델 가지치기와 텍스트 요약의 설명은 원문에 연결된 서빙 논문을 참고했습니다. [3]

MixLM은 긴 문서의 표현을 임베딩 토큰으로 캐시에 저장하고, 검색할 때 질의와 필요한 원문 필드에 섞어 랭커에 넣습니다. 인코더와 랭커를 함께 학습해 압축 표현도 랭킹에 유용하도록 만듭니다. [4]

“1개 임베딩 토큰”은 “단어 하나”가 아닙니다.

긴 내용을 학습된 숫자 벡터로 표현해 입력 위치 하나에 넣는다는 뜻입니다. 정보를 완벽하게 보존하는 압축 파일처럼 이해하면 안 됩니다.

블로그에서는 두 0.6B 모델과 단일 임베딩을 사용하는 구성을 설명합니다. [1]

후보 검색용 임베딩과 랭킹용 압축 임베딩의 차이

검색용 벡터는 질의 벡터와 비교해 후보를 찾는 데 씁니다. 랭킹용 압축 벡터는 랭커의 입력에 넣어 후보를 평가하는 데 씁니다. 모두 숫자 표현이지만 목적과 사용하는 위치가 다릅니다. 같은 벡터를 공유한다고 가정하면 안 됩니다.

NDCG@10은 상위 10개에 좋은 결과가 얼마나 앞쪽에 배치되는지 평가하는 점수입니다. 0.9239를 “정확도 92.39%”로 읽으면 안 됩니다.

수치를 이렇게 읽으면 정확합니다.

원문 대비 NDCG@10은 0.0193 감소했고, 상대 감소율은 약 2.05%입니다. 임베딩 압축은 가지치기·요약 구성보다 처리량이 10배이며, NDCG@10도 소폭 높습니다.

위 비율은 표에서 계산한 값입니다. 75.9배를 검색 전체의 응답 시간 개선이나 비용 절감률로 바꿔 말할 수 없습니다. EBR과 SLM도 서로 다른 일을 하므로 처리량만으로 우열을 비교하지 않습니다.

06 / MAKING RESULTS UNDERSTANDABLE

검색 결과 옆에 “왜”를 보여준다

왜 이 사람이 나왔을까?

People Search는 질의와 프로필 문구의 의미 유사도로 관련 부분을 골라 스니펫과 강조 표시를 만듭니다.

검색어를 어떻게 이해했을까?

질의의 의도와 조건을 짧게 설명하고, 해석 결과를 캐시해 재사용합니다.

원문의 “Explainability in search”와 “Reasoning”을 요약했습니다. [1]

사용자는 설명을 보고 원하는 조건이 반영됐는지 확인할 수 있습니다. 이때 보여주는 설명은 사용자용 해석 요약이므로, 모델 내부 계산을 그대로 공개한 기록으로 볼 필요는 없습니다.

07 / KEEP THESE IDEAS

기억할 것은 모델 이름보다 역할의 분담

  1. 이해 → 검색 → 랭킹을 나누면, 단계마다 필요한 계산을 선택할 수 있습니다.
  2. 평가 기준이 학습의 방향을 정합니다. 모델이 잘한다는 말을 하려면 무엇을 잘해야 하는지부터 정해야 합니다.
  3. 미리 계산하고 재사용하면 요청 시점의 일이 줄어듭니다. 작은 모델과 짧은 입력은 서로 다른 비용 절감 수단입니다.
Embedding · 임베딩
텍스트 등의 정보를 모델이 다룰 수 있는 숫자 벡터로 표현한 것.
SLM · 작은 언어모델
상대적으로 적은 파라미터를 가진 언어모델. 여기서는 후보 평가에 사용됩니다.
Bi-encoder / Cross-encoder
질의와 문서를 따로 표현해 비교하는 방식 / 함께 입력해 상호 관계를 평가하는 방식.
Distillation · 증류
교사 모델의 출력이나 판단 패턴을 학생 모델이 배우도록 학습하는 방법.
Offline / Nearline / Online
미리 일괄 계산 / 변경 후 빠르게 갱신 / 사용자 요청 중 계산.
Precision / Recall / NDCG
찾은 것의 적합성 / 정답을 놓치지 않은 정도 / 좋은 결과를 앞에 놓은 정도.

08 / IF NO GPU IS AVAILABLE

첫 검색은 기본 정렬, 다음엔 캐시된 점수로

GPU 없이도 시도할 수 있는 비동기 랭킹 제안입니다. 캐시에 점수가 없는 첫 요청은 검색 결과를 빠르게 보여주고, CPU 작업자가 뒤에서 SLM 점수를 계산해 저장합니다. 같은 검색을 다시 하면 아직 유효한 점수를 찾아 순위를 보정합니다.

설명용 제안 · LinkedIn의 실제 캐시 적재 흐름이라는 뜻은 아님

캐시된 점수를 안전하게 재사용하기 위한 키 예
요소왜 필요한가
정규화한 질의공백이나 표기만 다른 반복 검색을 같은 질의로 인식
공고 ID + 내용 버전공고가 수정되면 옛 점수를 새 본문에 재사용하지 않도록 함
랭커 모델 버전모델을 바꾸면 이전 모델의 점수를 새 점수와 섞지 않음
개인화 신호개인화 점수도 캐시한다면 관련 문맥이 다른 요청과 섞이지 않도록 구분
첫 검색의 SLM 순위까지 빨라지는 방법은 아닙니다.

처음 본 질의에는 아직 점수가 없으니 기본 정렬로 응답합니다. 입력이 많은 요청이 CPU 대기열을 막지 않도록 작업 수와 우선순위를 제한해야 하고, 글의 점수 캐시·랭킹 깊이 제어와도 함께 생각할 수 있습니다. LinkedIn 원문은 이런 최적화 요소를 언급하지만, 위의 CPU 미스 처리 흐름을 공개된 실제 구현이라고 설명하지는 않습니다. [1]

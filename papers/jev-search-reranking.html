둘 다 응답은 JSON일 수 있다. 서버가 숫자를 JSON으로 포장하는 일과, 모델이 JSON 문자열을 토큰별로 생성하는 일은 구분해야 한다.

GPT가 입력 전체를 매 토큰마다 처음부터 다시 계산한다는 뜻은 아니다. KV 캐시 같은 최적화가 있다. 여기서 보는 차이는 출력의 순차 의존성이다. OpenAI도 출력 길이 축소를 지연 최적화 수단으로 설명한다. 공식 최적화 가이드 ↗

공유 문맥 표현 / KV→질문별 분기→선택지 점수·확률→JSON 직렬화
  • KV 캐시: 문맥을 읽으며 계산한 중간값을 재사용하는 장치. 공유하더라도 각 질문이 문맥을 참조하는 계산은 남는다.
  • 어텐션 마스크: 어떤 부분이 다른 부분을 볼 수 있는지 제한하는 방식. 질문 격리를 구현할 수 있는 후보이며, Jev의 실제 마스크가 공개됐다는 뜻은 아니다.
  • 아직 확정할 수 없는 것: 기반 모델·파라미터 수, encoder/decoder 계열, 별도 분류 헤드, MoE 사용 여부, 정확한 손실함수.

‘보정된 확률’은 무슨 뜻일까?

“맞을 확률 80%”라고 예측한 사례를 충분히 모았을 때, 실제로 약 80%가 맞으면 보정(calibration)이 잘 된 것이다. 개별 답 하나의 정답을 보증하는 말은 아니다. 보정의 의미 ↗

맞음 80틀림 20

“80%”라고 예측한 가상의 100건

80건이 맞고 20건이 틀린 모습은 이상적인 보정을 설명하는 예다.

같은 100건 중 50건만 맞았다면, 예측 확률이 실제 성과보다 높았던 것이다.

이해를 위한 가상 도식 · Jev의 실제 정확도나 벤치마크 결과가 아님

정확도와 보정도 다르다. 많이 맞히는지와, 말한 확률이 실제 빈도와 맞는지를 각각 평가해야 한다. TypeSafe의 학습 목표가 모든 업무에서 이미 달성됐다는 뜻은 아니다.

확률 0.8과 confidence 0.8은 다르다.

Choice의 confidence는 별도 정답 판정 모델의 답이 아니다. 가장 높은 확률이 균등분포보다 얼마나 높은지 계산한다. 보기 3개에서 최대 확률 0.8이면 confidence는 0.7이다. 공식 계산식 ↗

05핵심 원리

여러 판단의 확률을, 하나의 점수로.

각 평가 단계의 확률에 단계 값을 곱해 평균낸다. 가장 유력한 단계 하나만 고르는 것보다 중간 판단을 보존한다. 기본 기준은 10단계, 사용자 정의 기준은 2~10단계다. 점수 계산 ↗

score = Σ(단계 확률 × 단계 값) / Σ(단계 확률)

08실무에서 기억할 것

후보, 점수, 실패 처리를 함께 설계한다.

  1. 후보 수와 반환 수를 분리

    size는 반환 수, candidateSize는 평가 후보 상한. 벡터의 knn.k는 따로 늘려야 한다. 없는 후보를 리랭킹이 되살리지는 못한다. 후보 설정 ↗

  2. 문서 길이에 맞춰 배칭

    원문 구현은 입력 크기로 묶고 문서를 임의 절단하지 않는다. 30질문 비교에서 적응형 배칭은 호출·관측 지연을 줄였고 nDCG@10 하락은 없었다. 원문 ↗

  3. 같은 문서 버전, 완전한 평가

    검색·평가가 같은 읽기 스냅샷을 사용한다. 모든 점수가 유효해야 순서를 바꾼다. GeekNews ↗

  4. 실패 시 정책을 명시

    기본값은 오류 반환. 허용되는 제공자 오류에는 returnOriginal로 원래 순서를 반환할 수 있다. 일부 평가 점수만 섞지는 않는다. 실패 처리 ↗

내 질문과 정답 문서를 작은 평가 세트로 고정하고, 같은 후보에서 순위·지연·사용량을 함께 비교하자.

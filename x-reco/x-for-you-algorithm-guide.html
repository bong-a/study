CHAPTER 02 · RETRIEVAL

후보 게시물은
세 곳에서 온다

전체 게시물에 무거운 모델을 돌리는 것은 너무 비쌉니다. 먼저 빠른 후보 수집기가 “볼 만한 몇 묶음”을 줄여 줍니다.

후보 수집의 목표는 완벽한 순위가 아니라, 좋은 게시물을 놓치지 않는 작은 풀(pool)을 만드는 것입니다.

후보끼리는 서로 답을 보여주지 않는다

Transformer 안에서 후보는 다른 후보를 참고하지 않고 사용자 문맥만 봅니다. 그래서 같은 게시물의 점수가 함께 들어온 후보 묶음에 따라 흔들리지 않고, 캐시하기도 쉬워집니다.

Hash embeddings

새 게시물도 바로 숫자로 표현한다

Retrieval과 Ranking은 여러 해시 함수로 임베딩을 찾습니다. 별도 단어 사전을 계속 관리하지 않아도 새 게시물을 즉시 표현할 수 있다는 설계입니다.

최종 점수 = Σ (행동 가중치 × 그 행동의 예측 확률)

예를 들어 답글 확률 4%와 답글 가중치 5.0은 점수에 +0.20을 보탭니다. 신고 확률 0.1%와 신고 가중치 -234는 -0.234를 보탭니다.

!
가중치를 “노출 배수”로 읽으면 안 됩니다.

답글 5.0은 답글 하나가 노출을 5배 만든다는 뜻이 아닙니다. 아직 일어나지 않은 행동의 예측 확률에 곱해지는 점수 계수이며, 행동마다 기본 발생 빈도도 다릅니다.

결정 이유를 남기기

어떤 소스, 필터, 점수, 규칙이 영향을 줬는지 기록해야 운영과 사용자 설명이 가능합니다.

decision_log
# 요청마다 실행되는 아주 작은 추천 파이프라인
context = load_viewer_context(viewer)

candidates = parallel(
    recent_from_following(context),
    similar_posts(context),
    interest_clusters(context)
)

candidates = pre_filter(candidates, rules=[
    duplicate, too_old, already_seen, blocked, no_access
])

for post in candidates:
    p = model.predict_actions(context, post)
    post.score = sum(weights[action] * p[action])

ranked = rerank_for_diversity(candidates)
visible = [post for post in ranked
           if visibility(viewer, post) != DROP]

return blend(visible, ads, prompts)

오해를 막는 네 개의 안전핀

×“답글 하나는 5배 노출”

가중치는 관측된 행동 횟수에 곧장 곱하는 배수가 아니라, 모델이 예측한 행동 확률을 점수로 바꾸는 계수입니다.

×“점수만 높으면 무조건 노출”

랭킹 뒤 Visibility Filtering이 DROP하면 제외됩니다. 순서 결정과 출입 결정은 다른 시스템입니다.

×“저장소가 production 전체”

일부 프롬프트·규칙과 배포 인프라가 빠져 있고, 모든 컴포넌트가 end-to-end로 빌드되도록 공개된 것도 아닙니다.

×“숫자는 앞으로도 고정”

기본 설정은 주요 production 값과 실험 변화에 맞춰 갱신될 수 있습니다. 분석에는 커밋과 확인일을 함께 남겨야 합니다.

30초 이해도 확인

Q1. Phoenix Retrieval과 Phoenix Ranking은 같은 일인가요?

아닙니다. Retrieval은 거대한 게시물 집합에서 가까운 후보를 빠르게 찾고, Ranking은 모인 후보 각각에 대해 여러 행동 확률과 점수를 계산합니다. 같은 Phoenix 모델 계열이지만 파이프라인 책임이 다릅니다.

Q2. INTERSTITIAL이면 게시물이 피드에서 사라지나요?

아닙니다. 게시물은 남지만 사용자가 탭해서 통과할 수 있는 경고 화면 뒤에 놓입니다. 참고로 경고 UI를 그리는 코드는 이 저장소에 포함되지 않았습니다.

Q3. SimClusters가 찾은 글도 Phoenix와 같은 모델로 랭킹되나요?

예. 공식 README는 in-network와 out-of-network 후보가 함께 모여 같은 랭킹 모델로 평가된다고 설명합니다.

CHAPTER 08 · GLOSSARY & SOURCES

용어를 붙잡고
공식 코드로 넘어가기

처음부터 저장소 전체를 읽지 마세요. 이 용어집으로 문장을 해석한 뒤, 궁금한 결정이 있는 파일만 따라가는 편이 훨씬 빠릅니다.

Candidate · 후보

아직 최종 노출이 결정되지 않은 게시물. 여러 소스가 찾은 뒤 필터와 랭킹을 거칩니다.

Candidate Pipeline · 후보 파이프라인

후보를 조회·보강·필터·점수화·선택하는 공통 실행 뼈대. X의 home-mixer는 이 프레임워크에 실제 For You 부품과 설정을 꽂습니다.

Home Mixer

For You 요청을 받아 Post Pipeline과 Blending Pipeline을 조립·실행하는 서비스. 후보 소스, 점수기, 필터, 선택기와 각종 클라이언트를 연결합니다.

Retrieval · 후보 수집

거대한 전체 집합을 빠르게 줄이는 단계. 정확한 최종 순위보다 좋은 후보를 놓치지 않는 것이 중요합니다.

Hydration · 정보 채우기

ID뿐인 요청·후보에 필요한 속성을 붙이는 일. 본문, 작성자, 언어, 라벨, 참여 수치 등을 가져옵니다.

In / Out-of-Network

팔로우 관계 안 / 밖. OON은 새로운 발견을 담당하지만 추가 할인·전용 필터가 적용될 수 있습니다.

Embedding · 임베딩

사용자·게시물의 특징을 숫자 벡터로 표현한 것. 가까운 벡터를 찾아 비슷한 취향과 내용을 연결합니다.

Transformer

순서와 문맥을 함께 읽는 신경망 구조. Phoenix는 최근 행동 시퀀스를 문맥으로 후보의 여러 행동 확률을 예측합니다.

Scorer · 점수기

후보에 숫자 점수를 붙이는 단계. Phoenix 예측, 가중합, 다양성·OON 조정 등이 연속으로 작동합니다.

Visibility Filtering

사용자와 게시물 조합별 노출 가능 여부 판단. 점수와 별개로 ALLOW, INTERSTITIAL, DROP 중 하나를 답합니다.

Interstitial · 경고 화면

민감할 수 있는 콘텐츠 앞에 놓는 확인 장벽. DROP과 달리 사용자가 통과해 게시물을 볼 수 있습니다.

Label · 라벨

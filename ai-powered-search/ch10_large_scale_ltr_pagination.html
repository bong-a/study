01 / FIVE DIFFERENT COUNTS

100개·40개·500개는 서로 다른 수입니다

기존 OpenSearch 실습의 서로 다른 규모
구분기존 실습대규모에서 결정할 것
학습·평가 검색어 Q105개, 학습 94 / 평가 11카테고리·의도·빈도·신상품을 충분히 대표하는가
검색어별 판정 문서 m평균 약 37개, 총 3,861행비슷한 정답과 어려운 오답이 들어 있는가
전체 카탈로그 N영화 65,702건저장·색인·갱신·후보 검색을 감당하는가
재정렬 예산window_size=500 / 샤드비싼 특징과 모델을 몇 개 후보에 적용하는가
페이지 크기 P상위 5개 반환한 번에 보는 수와 후속 페이지 정책

100개 검색어로 배운 모델도 처음 보는 검색어와 많은 문서에 점수를 계산할 수 있습니다. 다만 큰 커머스의 다양한 의도를 잘 일반화한다는 증거로는 작은 표본이 부족할 가능성이 큽니다. 학습 품질은 분포·라벨·특징·검증으로 판단하고, 페이징은 별도 서비스 계약으로 다룹니다.

상품마다 모든 검색어의 정답을 준비할 필요는 없습니다.

학습에서는 대표적인 검색어–상품 관계를 표본으로 배웁니다. 검색에서는 새 상품의 제목 일치·속성·가격·배송 등 특징을 계산해 같은 모델에 넣습니다. 신상품이 학습에 없었다는 사실만으로 점수화가 불가능해지지는 않습니다.

02 / TRAINING COVERAGE

검색어 종류와 판정 깊이를 따로 늘립니다

“몇 개면 충분한가?”에는 고정된 정답이 없습니다. 고정한 평가 세트에서 학습량을 늘렸을 때 얻는 개선과, 실패하는 검색어 집단을 함께 봅니다. 인기 검색어만 늘리면 숫자는 커져도 긴 꼬리 검색·신상품·희귀 속성은 계속 약할 수 있습니다.

학습 표본 구성의 출발점 · 설계 제안
축포함할 예누락하면 생기는 문제
검색 의도제품명, 카테고리, 브랜드+속성, 용도, 호환성정확한 제품 검색과 탐색형 검색을 같은 방식으로 처리
빈도head·torso·tail을 실제 로그 분포로 구분인기 검색어 평균만 좋아지고 희귀 검색 악화
상품 생애주기신상품, 인기·저노출 상품, 품절기존 인기 상품만 계속 우대
조건·사용자 맥락가격, 배송 지역, 언어, 기기, 필터같은 문구의 다른 구매 조건을 놓침
어려운 오답키워드는 맞지만 규격·호환성이 틀린 상품겉으로만 비슷한 상품이 상위에 노출

사람이 판정한 기준 세트에 노출·클릭·장바구니·구매 로그를 연결하고, 틀리기 쉬운 표본을 추가합니다. 자동 라벨은 사람 기준 세트로 정확도를 점검하세요. 보이지 않은 상품을 ‘클릭하지 않았으니 비관련’으로 처리하면 안 됩니다.

판정 행 수 ≈ Q × m
양방향 비교 수 = Σq 2 × pq × nqp는 관련, n은 비관련으로 판정된 문서 수입니다. 가상의 40개 판정이 관련 5개·비관련 35개이면 검색어당 방향 있는 쌍은 350개입니다.

대규모에서는 가능한 쌍을 전부 파일로 만들기보다 쿼리 그룹을 보존하며 미니배치·그룹 단위로 학습하고 필요하면 비교 쌍을 표본화합니다. 어려운 오답과 무작위 오답을 섞고 표본 비율도 기록합니다.

학습량을 얼마나 늘릴지 결정하는 방법

Q=100 → 500 → 2,000 → 10,000처럼 학습 곡선을 그릴 수 있습니다. 이는 실험 설계 예시이며 필수 기준이 아닙니다. 평가 데이터와 특징·모델 설정은 고정하고 NDCG@K·Recall@R을 카테고리/빈도별로 봅니다.

검색어 또는 의도 그룹과 시간을 나눠 누출을 줄이세요. 새 검색어 일반화, 미래 트래픽, 신상품 성능은 서로 다른 테스트입니다. 반복 조정에 쓸 검증 세트와 마지막에 볼 테스트 세트도 분리합니다.

대표 표본과 자동 판정을 연결한 실제 사례는 08절의 Etsy 2026을 참고하세요.

R·K·B는 병합 후 전역 후보 수입니다. OpenSearch의 rescore.window_size는 샤드별 수이므로 같은 값으로 해석하면 안 됩니다. 위 구조는 전역 후보를 랭킹 서비스에서 처리하는 제안이며, 기존 단일 샤드 실습을 그대로 운영으로 확장한 구현은 아닙니다.

좋은 상품이 후보에 없으면 모델도 끌어올릴 수 없습니다.

후보 단계는 Recall@R, 랭킹 단계는 NDCG@K 등을 따로 봅니다. 검색 누락인지 잘못된 순서인지 구분해야 올바른 단계를 개선할 수 있습니다.

04 / WHY PAGINATION BREAKS

페이지를 자르는 시점에 따라 결과가 달라집니다

서로 다른 문제를 구분하세요
방식문제대책
페이지를 자른 뒤 각 페이지만 LTR2페이지의 더 좋은 상품을 1페이지로 옮길 수 없음. 중복 없이도 전체 순위가 틀릴 수 있음후보 범위를 먼저 정렬하고 나중에 분할
매 요청 새 결과를 정렬하고 offset 증가상품 추가·삭제로 이전 상품이 다시 나오거나 건너뜀문서 스냅샷 또는 확정 결과 목록
후보 100개 중 20개만 반환하고 원본 커서는 100번째로 이동아직 안 보여준 80개가 누락미노출 후보 보관·화면 커서 별도 관리
LTR 마지막 점수를 BM25 search_after로 사용커서의 정렬 기준이 달라짐후보 수집 커서와 화면 커서 분리
직접 비교 · 가상의 상품·점수

같은 후보라도 페이지가 이렇게 달라집니다

8개 가상 상품 A–H입니다. 실제 기업의 상품·로그·점수가 아닙니다. 오른쪽은 처음 후보를 정렬해 고정한 결과입니다.

페이지부터 분할

페이지상품 ID · LTR 점수
1A(72), B(40)
2C(98), D(95)

정렬 후 순서 고정

페이지상품 ID · LTR 점수
1C(98), D(95)

왼쪽은 점수 98인 C가 2페이지에 남습니다. 페이지별 정렬만으로는 선택한 후보 전체의 순서를 맞출 수 없습니다.

예제의 전체 후보 보기

BM25 순서: A, B, C, D, E, F, G, H
LTR 점수: A=72, B=40, C=98, D=95, E=30, F=88, G=20, H=85
변경 시나리오의 새 상품 X=99. 고정 세션에는 즉시 끼어들지 않고 다음 검색에서 반영됩니다.

05 / RECOMMENDED STARTING DESIGN

확정된 ID 목록과 별도의 페이지 커서를 둡니다

이 질문에 대한 설계 제안 첫 요청에서 제한된 후보를 정렬한 뒤 ordered_ids를 세션 캐시에 저장합니다. 2페이지부터는 같은 배열의 다음 구간을 사용합니다. 이는 보관한 후보 집합 안의 순서를 유지하며 전체 카탈로그를 전역 정렬했다는 보장은 아닙니다.

  1. 검색어·필터·지역·정렬과 사용자 맥락을 정규화하고 모델·특징 버전을 선택합니다.
  2. 후보를 병합하고 정렬합니다. 판매 정책·다양성 규칙까지 반영한 최종 순서를 저장합니다.
  3. 페이지 크기도 세션에 고정합니다. 세션 ID·다음 검사 위치·만료 시각을 담은 커서를 반환합니다. 서버에서 서명과 세션 소유·조건을 검증합니다.
  4. 후속 페이지는 같은 목록을 읽고 판매 가능 여부를 확인합니다. 페이지 응답 ID 구간도 저장해 재시도·뒤로 가기를 일관되게 처리합니다.
저장할 상태의 개념 예시 · 실제 토큰은 불투명하게 전달
구조 설명용 예제
{
  "session_id": "opaque-session-id",
  "context_hash": "query + filters + sort + locale + user/cohort + feature_version",
  "model_version": "ltr-v7",
  "expires_at": "server-defined TTL",
  "ordered_ids": [
    "C",
    "D",
    "F",
    "H",
    "A",
    "B",
    "E",
    "G"
  ],
  "next_candidate_index": 2,
  "page_size": 2
}

사용자 커서는 OpenSearch의 search_after와 별개입니다. 앞의 것은 화면에 어디까지 전달했는지, 뒤의 것은 후보 검색 순서에서 어디까지 읽었는지입니다. 후보 수집을 끝냈다면 ID 목록을 페이지로 나누는 동안 PIT를 계속 붙잡을 필요도 없습니다.

품절 제외·중복 재시도를 고려한 페이지 의사 코드
구조 설명용 예제
# 설계 의사 코드: 서버 측 세션과 페이지 응답 캐시를 사용합니다.
def page(session, cursor, page_size):
    validate_owner_context_signature_and_expiry(session, cursor)
    assert page_size == session.page_size  # 크기를 바꾸면 새 세션
    key = (session.id, cursor.next_candidate_index)
    if saved_page := load_page(key):
        return render_current_availability(saved_page)

    pos = cursor.next_candidate_index
    ids = []
    while pos < len(session.ordered_ids) and len(ids) < page_size:
        # 실제 구현은 조회 수/시간 예산도 제한하고 짧은 페이지를 허용
        candidate = session.ordered_ids[pos]
        pos += 1
        if is_eligible_now(candidate, session.context):
            ids.append(candidate)

    response = make_page(ids, next_index=pos)
    # 동시 요청은 한 결과만 채택하고 재요청에도 같은 ID 구간을 사용
    saved_page = save_if_absent_and_read(key, response)
    return render_current_availability(saved_page)

TTL·첫 페이지 예산·재시도 정책은 서비스별로 정합니다. 같은 커서 재시도에서는 새 상품으로 다시 채우지 않고 저장된 ID 구간을 재사용하는 정책이 단순합니다. 새로 품절된 상품은 품절 표시하거나 제외하되 이미 정한 다음 커서 위치를 뒤로 당기지 않습니다.

06 / BOUNDARY & FRESHNESS

끝없이 같은 품질의 순위를 약속하지 않습니다

B개를 다 보여 준 뒤에는 제품 정책이 필요합니다. 아직 점수화하지 않은 모든 상품까지 고려한 정확한 LTR 순서를 얻으려면 더 많은 계산이나 별도의 정당한 가지치기 근거가 필요합니다. 커서만 바꿔서는 이 계산을 없앨 수 없습니다.

B개 이후의 선택지 · 설계상의 절충
선택얻는 것감수할 것
상위 B개 제공 후 조건 좁히기단순하고 일정한 품질·응답 시간무제한 탐색 요구는 충족하지 못함
뒤쪽은 저렴한 랭킹으로 이어 붙이기계속 탐색 가능하나의 전역 LTR 순서 보장 없음. seen IDs·별도 후보 커서 필요
다음 후보를 미리 가져와 추가 랭킹후속 페이지 지연을 줄일 수 있음이미 본 앞 페이지보다 좋은 후보가 새로 발견될 수 있음
새 검색 세션으로 재평가최신 상품·모델 반영기존 페이지 위치와 순위 변경

순위는 고정해도 판매 가능 여부는 현재 상태여야 합니다

재고·배송 제한·삭제·권한은 응답 직전에 확인하고 가격·구매 가능 여부는 거래 단계에서도 검증합니다. 캐시 배열을 삭제·압축하면 다음 offset이 흔들립니다. 원래 배열은 유지하고 검사한 위치만 앞으로 이동시키세요.

ordered_ids = [A, B, C, D, E, F], 페이지 크기 = 2
B가 품절이면 → [A, C] 반환, next_candidate_index = 3
다음은 D부터 검사반환 개수 2를 커서로 쓰면 C를 다시 볼 수 있습니다. 커서는 ‘후보 배열에서 소비한 위치’입니다.

페이지를 채우려고 무한히 탐색하지 않습니다. 상품 검증을 묶어서 호출하고 검사 수·시간 예산을 두며, 필요하면 적은 결과와 다음 커서를 반환합니다. 조건이나 정렬을 바꾸면 기존 세션에 이어 붙이지 않고 새 검색으로 취급합니다.

07 / OPENSEARCH 3.3.2

PIT가 LTR 커서 문제를 모두 해결하지는 않습니다

실습 버전에서는 native rescore와 search_after를 직접 결합할 수 없습니다.

OpenSearch 3.3.2 소스와 로컬 클러스터에서 확인했습니다. 다른 버전이나 별도 랭킹 경로까지 동일하다고 일반화하지 않습니다.

조회와 임시 PIT만 사용했고 PIT는 닫았습니다. 점수 내림차순 단독 정렬은 내부 최적화로 별도 sort 객체가 없어지고 search_after는 그 객체를 요구합니다. 다른 정렬 필드를 추가하면 rescore의 sort 제한에 걸립니다. rescore·sort 검사 ↗ · 점수 정렬 최적화 ↗ · search_after 검사 ↗

실습을 확장할 때: 고정 창 안에서 페이지 나누기

PIT + 고정 window_size + from/size를 사용하고 모델·요청 특징을 고정합니다. 노출 범위는 from + size ≤ window_size로 제한하는 편이 명료합니다. W=500, 페이지당 20개면 최대 25페이지입니다. 매칭 문서가 적으면 그보다 일찍 끝납니다.

W는 샤드별 값입니다. 샤드 8개·W=500이면 최대 4,000개 후보를 재평가할 수 있습니다. 페이지마다 W를 늘리면 후보와 순위가 달라집니다. 깊이가 W를 넘으면 재정렬하지 않은 문서가 섞일 수 있으므로 단순히 index.max_result_window만 높여 해결하려 하지 마세요. 3.3 rescore 문서 ↗ · 후보 수집 범위 ↗

10 / PRACTICAL NEXT STEPS

현재 실습에서 운영 설계로 넘어가는 순서

  1. 기준 데이터를 만든다. 현재 105개 검색어 실습에서 카테고리·빈도·의도별 실패를 수집하고 고정 검증/테스트 세트를 분리합니다.
  2. 로그를 정리한다. request/session ID, 검색 조건, 상품 ID, model/feature version, 기기, 페이지/배치, 절대 순위, 실제 노출과 이후 행동을 연결합니다.
  3. 예산을 분리한다. R·K·B·P와 샤드별 W의 의미를 합의하고 품질·지연을 단계별로 측정합니다.
  4. 페이징 계약부터 검증한다. 고정 후보 목록, 만료 시 재검색 안내, 커서 재시도, 품절·필터 변경 처리를 확인합니다.
  5. 반복 실험으로 확장한다. 학습량·후보 수·모델을 한꺼번에 바꾸지 말고 고정 평가와 제한된 온라인 실험으로 확인합니다.

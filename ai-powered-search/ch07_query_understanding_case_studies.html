Overview

검색창과 검색엔진 사이에는 번역 계층이 있다

사용자가 쓰는 언어는 모호하고 생략이 많다. 반면 검색엔진은 필드, 필터, 지리 조건, 부스트, 정렬처럼 명시적인 연산을 요구한다. Query Understanding은 이 간격을 메우는 계층이다.

Detection

Charlotte라는 문자열 구간을 찾는다.

Linking

어느 Charlotte인지 canonical entity와 연결한다.

Planning

좌표·반경·카테고리를 실제 검색 연산으로 바꾼다.

엔티티 추출과 쿼리 생성은 분리한다

NER가 무엇을 언급했는지 찾는 단계라면, entity linking은 어떤 대상인지 결정한다. Query Planner는 그 결과를 어떤 필터와 검색 전략으로 실행할지 결정한다. 한 모델이나 한 검색 DSL에 세 책임을 섞지 않는 것이 공통 패턴이다.

Synthesis

공통 실무 아키텍처: 중간 표현이 중심이다

사례들을 종합하면 핵심은 특정 NER 모델이 아니라, 각 분석 결과를 타입이 있는 중간 표현으로 모으고 검증한 뒤 엔진 쿼리로 컴파일하는 구조다.

1 · Normalize
대소문자, 철자, 언어, 동의어, 단위, 복합 구문을 정규화하되 원문과 offset을 보존한다.
2 · Detect
FST·사전·규칙은 알려진 엔티티를, NER·분류기는 long-tail intent와 속성을 찾는다.
3 · Link
surface_form을 canonical ID, 좌표, 카테고리, 상품 속성에 연결하고 후보 confidence를 계산한다.
4 · Plan
키워드, 필터, geo, 부스트, vertical, retrieval 전략을 엔진 독립 Query Plan으로 만든다.
5 · Compile
검증된 필드·연산자만 Solr, Elasticsearch, OpenSearch, SQL 등 대상 DSL로 변환한다.
6 · Evaluate
zero-result, reformulation, click, conversion, relevance judge, A/B test로 각 단계를 따로 관찰한다.

      "confidence": 0.99
    }
  ],
  "constraints": [
    {"field": "price", "op": "lte", "value": 100000},
    {"field": "distance", "op": "within", "value": "10km"}
  ],
  "ranking": [{"signal": "rating", "weight": 1.4}],
  "fallback": {"preserve_lexical_query": true}
}
분석 방법은 경쟁 관계가 아니라 역할 분담 관계다
방법잘하는 일주요 위험권장 배치
FST·Trie·규칙알려진 도시·브랜드·연산자, 낮은 지연시간사전에 없는 표현과 문맥 중의성정밀도가 필요한 deterministic fast path
NER·분류 모델표현 변형, long-tail intent, 일반화entity ID 연결과 confidence 보정 필요사전 매칭의 recall 보완
Embedding어휘 불일치, 의미 후보 검색정확한 필터·수치 조건 표현이 약함candidate retrieval·enrichment
LLM parser복합 자연어를 스키마로 변환필드·연산자 환각, 비용, 지연시간JSON Schema 출력 + allowlist 검증
문자열 DSL을 바로 생성하지 않는다

먼저 typed Query Plan을 만들고 backend adapter가 최종 문법을 생성한다.

모르는 구문은 버리지 않는다

태깅되지 않은 원문을 lexical query로 보존해 recall 급락을 막는다.

confidence와 fallback을 계약에 넣는다

낮은 confidence의 필터는 soft boost로 낮추거나 기본 검색으로 되돌린다.

허용 필드와 연산자를 제한한다

특히 LLM 출력은 schema validation과 query budget을 통과해야 한다.

단계별 관측성을 남긴다

원문, 추출 엔티티, Query Plan, 최종 DSL, 결과 지표를 연결해 실패 위치를 추적한다.

PageRank와 가장 큰 차이

PageRank는 링크 그래프에서 페이지의 전역 권위도를 계산하는 질의 독립 신호다. LTR은 판단 라벨과 여러 특징으로 질의별 점수 함수를 학습한다. PageRank 값은 LTR의 입력 특징 하나가 될 수 있지만 두 방법은 같은 알고리즘이 아니다.

03 · Three approaches

한 점, 한 쌍, 한 목록 중 무엇을 학습 단위로 볼까

POINTWISE문서 하나씩

각 문서의 관련성 등급을 회귀·분류한다. 구현은 쉽지만 순서 자체를 직접 보지 않는다.

PAIRWISE문서 두 개씩

“A가 B보다 위여야 한다”를 학습한다. RankSVM과 RankNet이 대표적이다.

LISTWISE결과 목록 전체

예측 목록과 정답 목록의 차이를 손실로 본다. ListNet·ListMLE 계열이 대표적이다.

POINTWISE

(doc A, y=3), (doc B, y=1) 각각의 등급 오차를 줄인다.

PAIRWISE

A ≻ B, A ≻ C, B ≻ C 쌍의 방향을 맞힌다.

LISTWISE

[A,B,C]라는 전체 순열 또는 점수 분포가 정답 목록과 가까워지게 한다.

분류는 도구일 뿐

pointwise·pairwise는 기존 회귀·분류 도구를 활용하기 위한 문제 변환이다. 최종 사용자가 보는 것은 각 행의 라벨이 아니라 정렬된 목록이므로 목록 지표로 다시 평가해야 한다.

04 · Objectives

RankNet은 ‘A가 B보다 위일 확률’을 학습한다

같은 질의의 두 문서 i, j에 모델 점수 sᵢ, sⱼ가 있을 때, RankNet은 점수 차이를 시그모이드에 넣어 i가 더 위일 확률을 만든다.

Pij = 1 / (1 + exp(−σ(si − sj)))
Lij = − P̄ij log Pij − (1 − P̄ij) log(1 − Pij)
문서 A · 관련성 3sA = 1.2
A ≻ B
문서 B · 관련성 1sB = 0.4
손으로 계산하면

σ=1일 때 점수 차이는 0.8, 따라서 P(A>B)=sigmoid(0.8)≈0.690이다. 정답이 A 우선이라면 손실은 −log(0.690)≈0.371. 차이가 1.7로 커지면 확률은 약 0.846, 손실은 약 0.167로 줄어든다.

초기
P=0.690
학습 후
P=0.846

LambdaRank는 ‘순위를 바꿨을 때 NDCG 영향’을 기울기에 더한다

모든 쌍의 오류가 사용자에게 똑같이 중요하지 않다. 1위와 2위를 바로잡는 교환은 99위와 100위보다 훨씬 중요할 수 있다. LambdaRank는 RankNet 계열의 쌍별 기울기에 두 문서를 바꿨을 때의 |ΔNDCG|를 곱해 상단 순위에 학습 힘을 집중한다.

|λij| ∝ |ΔNDCGij| · 1 / (1 + exp(σ(si − sj)))

LambdaMART는 그 기울기를 부스팅 트리가 따라가게 한다

LambdaMART는 LambdaRank의 λ-gradient를 목표값처럼 사용해 회귀 트리를 한 그루씩 추가하는 MART(gradient boosted trees) 모델이다. 비선형 상호작용을 잘 포착하고 서빙이 빨라 고전적 실무 LTR의 대표 선택이 됐다.

FM(x) = ΣMm=1 η · fm(x)

ListNet은 목록을 확률 분포로 본다

ListNet의 직관적인 top-one 형태는 정답 등급과 모델 점수를 각각 softmax 분포로 만들고, 두 분포의 교차 엔트로피를 줄이는 것이다. 한 문서의 절대 오차보다 목록 안에서 차지해야 할 확률 질량을 맞춘다.

Pz(j) = exp(zj) / Σkexp(zk)  ;  L = −ΣjPy(j)log Ps(j)
05 · Ranking metrics

NDCG는 ‘높은 관련 문서를 앞에 놓았는가’를 본다

아래는 실무와 LTR 문헌에서 널리 쓰이는 exponential-gain 형태다. 자료에 따라 이득 함수와 로그의 밑은 다르게 정의될 수 있으므로 모델 비교에서는 동일한 정의를 고정해야 한다.

DCG@k = Σki=1 (2relᵢ − 1) / log2(i + 1)  ;  NDCG@k = DCG@k / IDCG@k

2^rel−1은 높은 등급의 이득을 크게 만들고, log₂(i+1)은 아래쪽 결과를 할인한다. IDCG는 같은 문서들을 가장 이상적으로 정렬한 DCG이므로 NDCG는 보통 0–1 범위가 된다.

거의 이상적인 목록

  1. 01문서 Arel 3
  2. 02문서 Brel 2
  3. 03문서 Crel 0
  4. 04문서 Drel 1
NDCG@4 = 0.9926

좋은 문서를 늦게 배치

  1. 01문서 Drel 1
  2. 02문서 Arel 3
  3. 03문서 Brel 2
  4. 04문서 Crel 0
NDCG@4 = 0.7364
MRR첫 정답이 얼마나 빠른가

MRR=(1/|Q|)Σ 1/rank₍first relevant₎. 정답 하나를 빨리 찾는 QA·내비게이션 질의에 어울린다.

MAP여러 정답을 얼마나 앞에 모았나

각 관련 문서 위치의 Precision을 평균한 AP를 다시 질의 전체에서 평균한다. 보통 이진 관련성에 사용한다.

NDCG등급과 위치를 함께 본다

관련성 등급이 여러 단계이고 상단 품질이 중요한 웹·상품 검색에 자연스럽다.

P@K / RECALL@K상단 정확도와 후보 회수

P@K는 상단의 정답 비율, Recall@K는 전체 정답 중 top-K가 회수한 비율이다.

한 지표로 끝내지 않는다

최적화 지표와 제품 목표가 다르면 오프라인 점수는 올라도 사용자 경험은 나빠질 수 있다. NDCG·Recall·지연시간·다양성·비즈니스 안전 지표를 함께 보고, 마지막에는 온라인 실험으로 확인한다.

07 · OpenSearch production

OpenSearch LTR은 검색 요청 안에서 top-N을 즉시 재정렬한다

OpenSearch의 공식 Learning to Rank 플러그인은 외부에서 학습한 XGBoost·RankLib 모델을 업로드하고, 검색 시 sltr로 후보를 재채점한다. 학습은 오프라인이지만 추론은 검색 요청 안에서 실행되므로 최종 순서가 바로 응답된다. 표준 배포판에는 OpenSearch 2.19부터 LTR 구성 요소가 포함된다.

전체 인덱스에 sltr를 직접 실행하지 않는다

공식 문서는 전체 인덱스에 모델을 적용하면 CPU 집약적이라고 경고하며 rescore.window_size로 상위 N개만 재정렬하라고 안내한다. 문서의 window_size: 1000은 사용 예시이지 운영 권장값이나 성능 보장값이 아니다.

window_size는 전체가 아니라 shard마다 적용된다

1,000만 문서 전체를 LTR로 평가하는 것은 아니지만, primary shard가 많으면 후보 수가 예상보다 크게 불어난다. 검색 요청은 각 primary shard의 primary 또는 replica 사본 하나를 방문하고, 각 shard가 자신의 상위 window_size개를 재정렬한다.

2노드는 tail latency와 처리량 문제를 키울 수 있지만 단일 요청 지연의 첫 원인이라고 단정할 수 없다. QPS 1에서도 느리면 설정과 모델을 먼저 보고, 동시 부하에서만 search queue와 CPU가 포화되면 노드 증설 효과가 크다. replica는 읽기 처리량과 장애 대응을 늘리지만 한 요청이 방문하는 shard 수를 줄이지는 않는다.

1,000만 문서는 건수보다 pri.store.size로 산정한다

문서 크기와 매핑에 따라 1,000만 건이 30GiB일 수도, 수백 GiB일 수도 있다. AWS의 검색 중심 OpenSearch 가이드는 primary shard 하나를 대략 10–30GiB로 시작하라고 권한다. shard가 너무 크면 복구와 검색이 무거워지고, 너무 많으면 LTR 후보와 조정 비용이 늘어난다.

공식 보장값이 아니라 출발점으로, 데이터 노드 3대 × 8 vCPU / RAM 32GiB / heap 약 16GiB, 빠른 SSD, replica 1개, window_size 25–100, 저비용 피처 10–20개 정도에서 시작해 목표 QPS와 장애 시나리오로 줄이거나 늘린다. 인덱스가 작고 QPS가 낮다면 2대도 충분할 수 있다.

공식 LTR 성능표는 없다

OpenSearch와 AWS 공식 문서는 전체 인덱스 실행 금지, top-N rescore, script feature 주의, 캐시·통계 API는 설명하지만 “1,000만 문서·N개 노드·QPS X에서 p95 Yms” 같은 LTR 전용 벤치마크는 공개하지 않는다. 따라서 예제의 took 값이 아니라 자신의 데이터와 질의 분포로 측정해야 한다.

08 · Failure modes

모델보다 데이터 경계와 서빙 일관성이 더 자주 문제를 만든다

RISK 01질의 누수

같은 qid의 문서가 train과 test에 나뉘면 새 질의 일반화 성능을 과대평가한다.

RISK 02위치 편향

위에 노출돼 클릭된 결과를 정답으로 쓰면 기존 랭커를 그대로 학습한다. 클릭 모델·무작위 탐색이 필요하다.

RISK 03학습–서빙 불일치

특징 계산 코드, 정규화 통계, 결측값 처리가 다르면 오프라인 성능이 재현되지 않는다.

RISK 04비싼 특징

좋은 특징도 top-N 전체에서 너무 느리면 쓸 수 없다. 캐시·사전 계산·단계형 랭킹이 필요하다.

RISK 05목표 대리 문제

클릭률만 높이면 낚시성 결과가 유리할 수 있다. 만족도·전환·안전 제약을 함께 본다.

RISK 06분포 변화

새 콘텐츠와 유행 변화로 특징 분포가 바뀐다. 모니터링, 재판단, 재학습 주기가 필요하다.

10 · Recap

이 일곱 문장만 남겨도 된다

01

LTR은 질의–문서 특징을 점수로 바꾸는 함수를 판단 데이터에서 학습하고, 같은 질의 안에서 정렬한다.

02

pointwise는 문서, pairwise는 문서 쌍, listwise는 목록을 학습 단위로 본다.

03

RankNet은 쌍의 순서 확률, LambdaRank는 ΔNDCG 가중 기울기, LambdaMART는 그 기울기를 따르는 부스팅 트리다.

04

NDCG는 높은 관련성 문서를 앞에 둘수록 크게 보상하며, 제품 목표에 맞는 다른 지표와 함께 써야 한다.

05

실전에서는 qid 단위 분할, 클릭 편향 보정, 특징 일관성, top-N 재랭킹이 모델 선택만큼 중요하다.

06

OpenSearch LTR 비용은 대략 primary shard × window × 피처 수 × 피처 비용으로 커지며, window_size는 shard마다 적용된다.

07

데이터 노드 2대는 동시 부하의 병목일 수 있지만, QPS 1에서도 느리다면 증설보다 피처·모델·캐시·window를 먼저 진단한다.
